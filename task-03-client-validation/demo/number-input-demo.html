Task 3 — Step 4: Input Type Evaluation Harness

Comparing native type="number" against controlled type="text" for numeric student admission identifiers. Isolated test harness hosted strictly within the assessment workspace.

Native Number Input FLAWED UX

An HTML <input type="number"> forces browser spin buttons and initialized numeric values. Correcting input creates the notorious 0400 error.

The Three-State Friction Sequence:
  • 1 Initial Load: Field initializes with default 0 and stepper arrows.
  • 2 User Types 400: Appends to 0, producing 0400 instead of 400.
  • 3 Correction Friction: User must move cursor back to beginning to delete leading zero.
Raw DOM Value: "0"

Controlled Text Input ACCESSIBLE UX

An HTML <input type="text" inputmode="numeric"> restricted via regex. Empty by default, no steppers, zero leading zero glitches, parsed with Number() on submission.

The Clean Sequence:
  • 1 Initial Load: Clean empty field with contextual placeholder.
  • 2 User Types 400: Instantly types 400 with no leading zero pollution.
  • 3 Submission: Parsed to integer via Number(val) on form submit.
Raw DOM Value: "" | Parsed Number: NaN

Assessment Evaluation: Where A Number Input Is the Correct Choice

A native type="number" input is the correct choice only when collecting discrete, quantifiable measurements that are mathematically operationalized and benefit from stepped increments, such as item quantities, ticket counts, or age. It is fundamentally incorrect for non-quantitative numeric identifiers (such as student admission numbers, credit card numbers, or postal codes), where leading zeros are meaningful, arithmetic operations are invalid, and spin buttons create accidental value mutation during mobile page scrolling.
